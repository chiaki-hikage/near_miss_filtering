# ZOD Sequences の時刻の対応の確かめ

2026-11-13。「多くの候補の検出区間がカメラの開始の前に終わる」という結果 (`out/zod/video_review/README.md`) の原因を調べた。

- スクリプト: `scripts/zod/time_alignment.py`
- 出力: `out/zod/time_alignment/20261113_r1/`
- ネットワークは使っていない

## 結論

| 疑い | 結果 |
|---|---|
| データ仕様の違い | **一部はそう。** カメラ・LiDAR・`info.json`・`metadata.json`・`ego_motion.json` は同じ約 20 s にそろっている。一方、`oxts.hdf5` は全件 50 s (カメラの 5 s 前〜25 s 後)、`vehicle_data.hdf5` は走行全体 (9〜243 分)。OXTS と車両データのファイルは、カメラの 20 s だけではない |
| 解析側の時刻の変換 | **問題は無い。** OXTS の時刻の式は SDK と同じ。SDK の `ego_motion.json` (カメラ・LiDAR の時刻の軽量版) は、全 1,473 件で OXTS を同じ時刻で補間した値と完全に一致した (ヨー角速度の差 0) |
| シーケンスの割り当て | **問題は無い。** 候補の時刻は、その OXTS を含むシーケンスに正しく割り当たっている (67 件すべてで配列の位置と時刻が一致) |
| **解析側の区間の作り方** | **主な原因。** Phase 2 の「始まり」(ピークから値が半分に下がるまで戻った時刻) に「閾値を超えていた長さ」を足して検出区間とした。持続型では「始まり」が閾値を超えた時刻より 1〜21 s 前になるため、区間が前にずれた |

**正しい区間で数え直すと、カメラと重なる候補は 67 件のうち 36 件だった。**

- 優先の候補 11 件のうち 9 件はカメラと重なる
- E0196 はカメラの開始の 0.01 s 前に終わる
- E0160 はカメラの後 (+28〜+39 s、OXTS だけの区間) にある

## 2. 公式 SDK の時刻の扱い (`zod` 0.8.0)

- `EgoMotion.from_oxts_path` (`zod/data_classes/ego_motion.py`): `timestamps = 1980-01-06 (GPS 元期) + timestamp + leapSeconds`。解析側の `signal_survey.load_oxts` と同じ式
- `ZodSequence.oxts` は OXTS の全体 (50 s)。`ZodSequence.ego_motion` は `ego_motion.json` (20 s、「light-weight version of oxts」とコメントにある)
  - SDK は `ego_motion` を LiDAR の動きの補正に使い、カメラの時刻 (`keyframe_time`) に合わせる
  - SDK に、OXTS を 20 s に切る処理は無い
- `VehicleData` は `timestamp/nanoseconds/value` をエポックのナノ秒として読む (`zod/data_classes/vehicle_data.py`)。解析側も同じ
- **確かめ**: `ego_motion.json` の角速度は、全 1,473 件で、OXTS (上の式) をその時刻で補間した値と一致した (差の最大 4×10⁻¹⁶)
  - Zenseact 自身が、同じ時刻の基準で、カメラ・LiDAR の 20 s を OXTS の 50 s の中に置いている
  - 前進速度は 13 件で合わなかった。13 件とも ZOD の `blacklisted` (14 件) に入っている

## 3. 時刻の物理的な確かめ (カメラの映像 vs OXTS)

- mini の 2 シーケンスで、画像の横の流れ (3 フレーム離れた画像の位相相関) と OXTS の方位の変化の相関を、ずれ ±10 s で調べた (前回は ±1 s だけ、`camera_sync_wide.csv`)
- 000000 (方位の変化が大きい): ずれ 0 で相関 0.67、最大は −0.45 s で 0.69 (−1.0〜−0.15 s が同じ程度)。±10 s の中にほかの山は無い。**5 s のずれは無い。** カメラと OXTS は約 ±1 s で合う
- 000002 (方位の変化がほとんど無い、標準偏差 0.09 deg): 相関が弱く (最大 0.37)、判断できない
- 車両データと OXTS の時計は、走行ごとに 0.01〜0.15 s のずれで、補正済み (`docs/zod_full_screening.md` §1.2)

## 4. 解析側の区間の誤り

Phase 2 の `event_features` の「始まり」(`t_onset`) は、ピークから値が半分に下がるまで戻った時刻。一方、`duration_s` は閾値を超えていた区間の長さ (配列の位置 i0〜i1)。

- **持続型 (5 s 平均) では、高い状態が閾値を超える前から続く**
  - 「始まり」は閾値を超えた時刻より 1.3〜21 s 前になる (`candidate_intervals.csv` の `onset_minus_run_start_s`)
  - 6 件は OXTS の区間の頭で打ち切られている (`onset_at_block_start`。本当の始まりは OXTS より前で分からない)
- **この 2 つを足した「始まり〜始まり + 長さ」を検出区間として使った所**

| 所 | 影響 |
|---|---|
| Phase 3 (`full_weather.py` の `event_physics`) | 舵角・トルク・β・ロールを見た区間が、本当の区間より 1.3〜21 s 前にずれた。**持続型の判定の物理の確かめは、区間を直して計算し直す必要がある** |
| Phase 3 の風の時刻 | 「始まり」を使った。ずれは最大 21 s。10 分値なので影響は小さいと見込むが、計算し直す |
| 映像の一覧 (`video_review.py`、`out/zod/video_review/20261113_r1/index.csv`) | カメラとの重なりを誤って数えた。例: E0096・E0082・E0004・E0148 は「0 s」とした (実際は 1.9〜3.9 s)、E0160 は「11.4 s」とした (実際は 0) |
| Phase 2 の `in_camera_sequences` | 「始まりの 2 s 前〜ピークの 2 s 後」で判断していて、広すぎた |

**影響が無い所**: Phase 2 の検出そのもの (閾値の超過、件数、仮説の割り当て) と、上位の候補の図 (ピークを中心に描いている)。

## 5. 直すこと

**2026-11-13 に実施した** (`docs/zod_event_time_fix.md`)。Phase 2 は `20261113_r7`、Phase 3 は `20261113_r4`、映像の一覧は `20261113_r2`。判定は 14 件とも変わらなかった。

1. 候補の区間を、閾値を超えていた区間 [t(i0), t(i1)] と、高い状態の始まり (打ち切りの有無つき) の 2 つに分けて持つ
2. Phase 3 の照合 (`full_weather.py analyze`) を、正しい区間で新しい実行 ID で計算し直す。持続型の判定 (支持・反証・不明) が変わりうる
3. 映像の一覧 (`video_review.py`) を、正しい区間で作り直す
4. 「カメラに入る」の判断は、閾値を超えていた区間とカメラの区間の重なりで行う
