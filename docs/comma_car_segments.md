# commaCarSegments のデータと信号
> データセット間の比較は [datasets.md](datasets.md) にまとめてある。

<https://huggingface.co/datasets/commaai/commaCarSegments>

comma2k19 で組んだ検出処理を、そのまま別のデータセットへ持ち込むための入力層の記録。
入力層の確認は `TOYOTA_RAV4_TSS2` の 15 セグメント (20.5 MB)、
スクリーニングは 196 セグメント (3.3 時間、0.26 GB) で行った。
現時点では暫定検証であり、確定仕様ではない。

---

## 1. comma2k19 との違い

|                | comma2k19                       | commaCarSegments                    |
| -------------- | ------------------------------- | ----------------------------------- |
| 分類           | ドライブ単位。車両は 2 台のみ   | **車種キー単位**。230 車種          |
| 規模           | 2,019 セグメント (33 時間)      | 188,883 セグメント (3,148 時間)。RAV4 TSS2 で 11,387 |
| 1 セグメント   | 60 秒                           | 60 秒                               |
| 中身           | `processed_log` + 映像 + 生 CAN | **`rlog.zst` のみ**                 |
| 復号済み信号   | 車速・舵角・輪速・レーダ        | **無い。すべて生 CAN から作る**     |
| 映像           | あり (20 Hz)                    | **無い**                            |
| 走行環境       | CA-280 の高速に限られる         | 限定なし                            |
| openpilot 介入 | 送信フレームからの推定のみ      | **`controlsAllowed` を直接取れる**  |

映像が無いことは、これまでの進め方 (候補を出して目視で確かめる) に直接効く。
このデータセットは「目視で確かめる対象」ではなく
「comma2k19 で決めた条件が他の車両・他の環境でどう振る舞うか」を見る対象として使う。

## 2. セグメントの指定と取得

`database.json` (9.4 MB) が 車種キー → セグメント名の一覧を持つ。

```
TOYOTA_RAV4_TSS2 → ["d0e756c10c7adf7a/00000004--a4e9cb8af7/36/s", ...]
                     └ dongle_id ──┘ └ route_id ─────┘ └ 番号
```

実データの URL は

```
{BASE}/segments/<dongle_id>/<route_id>/<番号>/rlog.zst
```

`<dongle_id>|<route_id>` を drive_id として扱うと、comma2k19 の
`<dongle_id>|<日時>` と同じ形になり、ドライブ単位のまとめ方を共通化できる。

### 取得量

ヘッダ実測 (12 件サンプル) で 1 セグメント平均 **1.38 MB** (1.24〜1.61)。

| セグメント数 | 概算    |
| ------------ | ------- |
| 15           | 21 MB   |
| 200          | 0.28 GB |
| 2,000        | 2.75 GB |
| 11,387 (全件)| 15.7 GB |

`scripts/fetch_car_segments.py --dry-run` と
`scripts/screen_segments.py --dry-run` は、取得前に必ずこの見積りを出す。

## 3. rlog の中身

openpilot のログを zstd で固めたもの。読むには cereal の capnp スキーマが要る
(`scripts/fetch_cereal_schema.py` が 5 ファイルだけ取ってくる)。

このデータセットの rlog は **間引かれている**。実測で入っていたのは 3 種類だけ。

| メッセージ    | 周期  | 内容                                            |
| ------------- | ----- | ----------------------------------------------- |
| `can`         | 100 Hz | 全バスの生 CAN フレーム (address, dat, src)     |
| `pandaStates` | 10 Hz | `controlsAllowed` ほか panda の状態             |
| `carParams`   | 1 件  | 車種判定 (`carFingerprint`)、諸元、VIN          |

`carState` / `radarState` / `modelV2` といった openpilot の復号済み信号は
**入っていない**。車速も舵角もレーダも、すべて生 CAN から作る。

### バス構成

実測で バス 0 = 車両、バス 1 = レーダ、バス 2 = 前方カメラ。
panda が バス 0 ↔ バス 2 を転送するため、同じアドレスが送信フラグ (`src` の 0x80) 付きで
二重に現れる。comma2k19 の `raw_can/src` と同じ規則
(下位 7 bit = バス番号、0x80 = 送信) だったので、フレームの選び方は共通にできた。

### 受信周期は車両ごとに違う

同じ `TOYOTA_RAV4_TSS2` でも、車両によって周期が違った。

| メッセージ         | 車両 A | 車両 B  |
| ------------------ | ------ | ------- |
| 0x24 KINEMATICS    | 50 Hz  | 76.9 Hz |
| 0x25 STEER_ANGLE   | 100 Hz | 76.9 Hz |
| 0x0AA WHEEL_SPEEDS | 100 Hz | 76.9 Hz |
| 0x0B4 SPEED        | 50 Hz  | 38.4 Hz |

さらに 0x2C1 (アクセル開度) は車両 B に無く、15 セグメント中 33% でしか復号できなかった。
**一様グリッドへの再サンプルと、信号の有無を許容する作りが前提になる。**

## 4. 層の分け方

車種依存の CAN ID / ビット定義を検出側に持ち込まないため、次の 4 層に分けてある。

```
生 CAN                     io/comma2k19.py        (processed_log/CAN/raw_can)
                           io/comma_car_segments.py + io/rlog.py  (rlog.zst)
   ↓ RawCanFrames          io/canonical.py         t / address / payload / src
正規化車両信号             io/can_decode.py + configs/vehicles/*.yaml
   ↓ SegmentData           io/canonical.py         チャネル名と単位だけ
   ↓ + RadarTracks         io/can_radar.py         (生 CAN からレーダを組む)
一様グリッド               signals.py
特徴量                     features.py
検出                       detectors.py + configs/detection.yaml
```

* `io/can_decode.py` と `io/can_radar.py` は CAN ID を持たない。すべて車種設定から渡る。
* `features.py` 以降はデータセットも車種も知らない。
* データセットを足すときは `sources.py` に `SegmentSource` を返す関数を 1 つ書く。

### 正規化チャネル名

| チャネル                     | 単位   | 向き               |
| ---------------------------- | ------ | ------------------ |
| `speed_mps`                  | m/s    | —                  |
| `steer_deg`                  | deg    | 左が正             |
| `ws_fl/fr/rl/rr_mps`         | m/s    | —                  |
| `yaw_rate`                   | deg/s  | 左旋回が正         |
| `accel_x`                    | m/s²   | 進行方向が正       |
| `accel_y`                    | m/s²   | 左が正             |
| レーダ `lateral_m`           | m      | **左が正**         |

レーダの横位置を左正にそろえるのは、`features.path_lateral_offset` が
ヨーレート由来の進路ずれ (左旋回で正) と直接引き算するため。
opendbc の `LAT_DIST` は右が正なので、車種設定の `radar.lateral_sign: -1.0` で反転している。

## 5. 復号する信号 (TOYOTA_RAV4_TSS2)

ビット定義の出典は opendbc:
`dbc/generator/toyota/toyota_nodsu_pt.dbc`、`_toyota_2017.dbc`、
`_toyota_adas_standard.dbc`、`dbc/toyota_tss2_adas.dbc`。
`factor` / `offset` は DBC の値をそのまま設定に書き、単位換算は `unit_in` / `unit` で行う
(電卓で潰すと opendbc との突き合わせができなくなるため)。

### comma2k19 の RAV4 (2017) との違い

| 項目              | RAV4 2017 (TSS-P) | RAV4 TSS2      |
| ----------------- | ----------------- | -------------- |
| BRAKE_MODULE      | 0x224             | **0x226**      |
| BRAKE_PRESSED bit | 5                 | **37**         |
| レーダ            | 0x210〜0x22F (DSU)| **0x180〜0x19F** (バス 1) |
| ACCEL_X の符号    | 反転が必要        | **不要**       |
| ACCEL_Y の符号    | 反転が必要        | **不要**       |

同じ車名でも別プラットフォームなので、車種設定を分けて持つ
(`toyota_rav4.yaml` / `toyota_rav4_tss2.yaml`)。

### 主系列

| チャネル       | 出所                                    |
| -------------- | --------------------------------------- |
| `speed_mps`    | **0x0AA の 4 輪速の平均** (下の 6 章)   |
| `steer_deg`    | 0x25 STEER_ANGLE (1.5 deg) + STEER_FRACTION (0.1 deg) |
| `yaw_rate`     | 0x24 YAW_RATE                           |
| `accel_x/y`    | 0x24 ACCEL_X / ACCEL_Y                  |
| レーダ         | 0x180〜0x18F (距離・横位置・相対速度) + 0x190〜0x19F (スコア) |

### comma2k19 では取っていなかった信号

| チャネル              | 出所                     | 使い道                                   |
| --------------------- | ------------------------ | ---------------------------------------- |
| `gvc_mps2`            | 0x320 VSC1S07 → GVC      | 車両が報告する前後 G。車速微分の裏付け   |
| `gas_pedal_pct`       | 0x2C1 GAS_PEDAL          | アクセル急 OFF → パニックブレーキ        |
| `brake_pressure` / `brake_position` | 0x226   | 踏力・踏み込み量 (単位不明、相対値のみ)  |
| `precollision_active` | 0x283 PRE_COLLISION (バス 2) | 純正 AEB。作動すれば車両側の危険判断     |
| `steer_torque_driver` | 0x260                    | openpilot 介入中に人が握っているか       |
| `op_engaged`          | pandaStates              | openpilot 介入区間 (推定不要)            |

`gvc_mps2` と `gas_pedal_pct` は comma2k19 の RAV4 でも同じ位置にあることを確認し、
そちらの車種設定にも足した (検出条件には未使用)。

### 無効にしてある信号

| 信号           | 理由                                                                 |
| -------------- | -------------------------------------------------------------------- |
| `BRKON`        | 点灯する (duty 5.4%) が、BRAKE_PRESSED (6.8%) と**一度も同時に立たない**。意味が確定しない |
| `TURN_SIGNALS` | 値 2 の区間は右旋回と整合したが、値 1 (左) は標本 147 点で確認できず。1 Hz で分解能も足りない |
| `HAZARD_LIGHT` | 15 セグメントで常に 0                                                |

## 6. 整合性の確認結果

`scripts/check_signal_parity.py` で 3 段階に確かめた。

### A. 復号経路の検証 — comma2k19 の `processed_log` と突き合わせる

commaCarSegments には突き合わせる相手が無いので、まず comma2k19 側で
「同じ raw_can から復号し直した値」が配布値と一致するかを見る。

| 主系列      | 生 CAN から復号   | 傾き    | rmse       | 判定       |
| ----------- | ----------------- | ------- | ---------- | ---------- |
| `speed_mps` | 4 輪速の平均      | 1.00000 | 0.0002 m/s | 一致       |
| `speed_mps` | 0x0B4 SPEED       | 1.02130 | 0.57 m/s   | **2.13% 高い** |
| 輪速 4 本   | 0x0AA             | 1.00000 | 0.0005 m/s | 一致       |
| `steer_deg` | 0x25 本体 + 端数  | 1.00000 | 0.0012 deg | 一致       |

**comma2k19 の配布車速は 4 輪速の平均そのもの**で、0x0B4 の SPEED は表示車速だった。
そこで commaCarSegments 側も `speed_mps` を 4 輪速の平均から作り、
0x0B4 は `speed_can_mps` として突き合わせ用に持つことにした。
表示車速の較正は車種ごとに違う (TSS2 の実測では輪速平均の 0.998 倍) ので、
主系列に使うとデータセット間の比較が崩れる。

### B. 物理整合の検証 — commaCarSegments 側

突き合わせる相手が無いので、信号どうしの物理関係で符号とスケールを確かめる。
期待する傾きは comma2k19 (220,181 点) での実測値。

| 確認                       | r     | 傾き   | comma2k19 | 判定 |
| -------------------------- | ----- | ------ | --------- | ---- |
| 車速 vs 輪速平均           | 1.000 | 1.000  | 1.000     | OK   |
| ax (車速微分) vs GVC       | 0.973 | 0.945  | 0.943     | OK   |
| ax (車速微分) vs ACCEL_X   | 0.933 | 1.047  | 0.996     | OK   |
| ay = v×yaw vs ACCEL_Y      | 0.866 | 0.696  | 0.703     | OK   |
| 舵角 vs ヨーレート (符号)  | 0.968 | —      | —         | OK   |
| 舵角の微分 vs STEER_RATE   | 0.878 | 0.838  | —         | OK   |

**ACCEL_X / ACCEL_Y の符号は comma2k19 の RAV4 と逆だった。**
2017 の設定をそのまま持ってくると r = −0.92 / −0.87 になる。
DBC の定義は同一なので車両側の実装差で、車種ごとに実測で決めるしかない。

`ay = v×yaw` に対して ACCEL_Y の傾きが 0.70 にしかならない点は、
comma2k19 でも 0.703 で**同じ比**だった。既存の急操舵の閾値
(`ay_kin > 2.0` と `ay_can > 1.4`、比 0.7) がそのまま持ち込める。

### C. 諸元の比較

15 セグメントの走行条件は、車速中央 26.4 m/s (95%tile 32.2)、
前後加速度 −0.54〜0.74 m/s²、openpilot 介入率 72.0%。
comma2k19 と同じく高速巡航が主体で、強い挙動は含まれていない。

## 7. 自転車モデルの当てはめ

`δsw = SR·L·(r/v) + SR·Kus·(v·r) + δoffset` を 14,675 点で当てはめた。

|                        | RAV4 2017 (comma2k19) | RAV4 TSS2 (15 セグメント) |
| ---------------------- | --------------------- | ------------------------- |
| R²                     | 0.973                 | 0.968                     |
| steer_ratio (当てはめ) | 16.75                 | 18.57                     |
| openpilot の値         | 16.88                 | 14.30                     |
| understeer_gradient    | 0.00235               | 0.00179                   |
| **ヨーレート残差 σ**   | **0.341 deg/s**       | **0.359 deg/s**           |

残差の大きさが同程度なので、`yaw_instability` の判定 (残差 6σ) はそのまま持ち込める。
一方 steer_ratio は openpilot の 14.30 と 30% 違う。openpilot の値は制御用の調律値で、
ここで要るのは「舵角からヨーレートを予測する残差が最小になる実効値」なので当てはめ値を使う。

ただし **15 分ぶん・3 車両をまとめた当てはめで暫定**。台数を増やす際は
車両ごとの再当てはめを検討する。

## 8. 現行センサで確認できないこと

comma2k19 で分かっていたことが、TSS2 でも変わらなかった。

| 見たいもの        | 状況                                                              |
| ----------------- | ----------------------------------------------------------------- |
| ABS 作動          | **判定できる** (0x226 `ABSACT`)。33 時間で 11 件。11 章参照     |
| VSC / TRC 介入    | 参照 DBC に `VSCACT` / `TRCACT` / `VDMACT` がある。33 時間で 0 件 |
| 純正 AEB          | `precollision_active` は 33 時間で 2 件。制動要求 [N] は常に 0   |
| 車線マーカ        | rlog が間引かれており `modelV2` が入っていない                     |
| 映像              | 配布されていない                                                   |

ABS / ESC / TCS を実データで確かめるには、降雨・降雪路や、より強い制動を含む
走行が要る。セグメント数を増やせば当たる可能性はあるので、
`scripts/screen_segments.py` は「その信号を復号できたセグメントの割合」と
「最大値」を必ず出す。全件 0 のままなら、条件が検証できていないことが結果に残る。

## 9. 使い方

```bash
# capnp スキーマを取る (最初の一度だけ)
uv run python scripts/fetch_cereal_schema.py

# 車種の一覧を見る
uv run python scripts/fetch_car_segments.py --list

# 取得量を確かめてから取る
uv run python scripts/fetch_car_segments.py TOYOTA_RAV4_TSS2 --routes 3 --per-route 5 --dry-run
uv run python scripts/fetch_car_segments.py TOYOTA_RAV4_TSS2 --routes 3 --per-route 5

# 整合性を確認する
uv run python scripts/check_signal_parity.py --platform TOYOTA_RAV4_TSS2

# 検出を回す
uv run python scripts/run_detection.py raw_data/comma_car_segments \
    --dataset comma_car_segments --platform TOYOTA_RAV4_TSS2 --out out/rav4_tss2

# 数百〜数千セグメントをスクリーニングする (取得と処理を重ねて流す)
uv run python scripts/screen_segments.py TOYOTA_RAV4_TSS2 --limit 500 --dry-run
uv run python scripts/screen_segments.py TOYOTA_RAV4_TSS2 --limit 500 --out out/screen_rav4_tss2 \
    --discard-cache          # 処理の済んだ rlog をその場で消す

# 類型ごとに代表候補を選んでプロットする
uv run python scripts/pick_cases.py out/screen_rav4_tss2 --top 2 --plot --span 20

# 1 件だけ細かく見る (前後のセグメントも繋いで、位置を指定して拡大)
uv run python scripts/plot_segment.py raw_data/comma_car_segments \
    --dataset comma_car_segments -s "63e74ebb84173067|0000009c--84e520ce41/2" \
    --context 1 --focus 2@25.5 --span 20
```

処理は 1 セグメント 0.35 秒 (読み出し 0.35 / 特徴量〜候補 0.01)。
所要時間はほぼ回線速度で決まる。中断しても `--resume` で続きから流せる。

### 最上位候補 — 検証済みのヒヤリハット

`63e74ebb84173067|0000009c--84e520ce41` セグメント 2 (severity 27.9)

```
abs_active | aeb_active | hard_brake | low_ttc | panic_brake |
panic_brake_with_lead | hard_accel | wheel_speed_anomaly
```

時系列を追うと、証拠が一本の筋になっている。

| 時刻 | 出来事 |
| ---- | ------ |
| 20.5〜24.3 s | openpilot 介入中、12 m/s で巡航。先行車 38 m、相対速度 -0.2 → -7.5 m/s |
|              | TTC 189 → 2.95 s、車間時間 3.17 → 1.78 s へ単調に悪化 |
| 24.9 s | **純正 PCS が作動** (`precollision_active` = 1)、ブレーキ踏み込み開始 |

## 11. ABS 作動フラグの取り違え

**`FABS` (0x320 bit 2) は ABS の「作動」ではなく「故障」フラグだった。**

これまで `abs_active` の判定に使っていたが、comma2k19 の 3.1 時間でも
commaCarSegments の 33 時間でも一度も立たなかった。理由が分かった。

0x320 VSC1S07 の F 系 (`FVSCM` / `FVSCSFT` / `FVSCL` / `FABS`) は故障フラグの並びで、
**ABS が明らかに作動している区間でも 0 のまま**だった。

正しい作動フラグは opendbc の参照 DBC (`opendbc/dbc/toyota_2017_ref_pt.dbc`) にある。

| 信号 | 位置 | 内容 |
| --- | --- | --- |
| `ABSACT` | 0x226 VSC1F06 bit 59 | **ABS 作動** |
| `VSCACT` | 0x226 bit 36 | VSC 作動 |
| `PMC` | 0x226 bit 1, 10 bit × 0.02 | マスタシリンダ圧 [MPa] |
| `SLP_WL` | 0x3B7 VSC1S95 bit 10, 3 bit | 滑り警告灯 |
| `TRCACT` / `VDMACT` / `ABSSLP` | 0x220 VSC2F07 bit 15 / 13 / 14 | TRC / VDM 作動、ABS スリップ |

openpilot の DBC は同じ 0x226 を `BRAKE_MODULE` として一部の信号しか定義していない。
**同じメッセージを、より詳しく定義した別の DBC が opendbc の中に同梱されている。**

参照 DBC の並びが正しいことは実測で確かめた。

* `WSTP` (bit 37) は openpilot の `BRAKE_PRESSED` と同一
* `PMC` は 0〜9.9 MPa で、制動の強さと整合する妥当な範囲
* `VSCEXIST` (0x3B7 bit 59) が全フレームで 1、`TRCOFF`/`VSCOFF` の位置も openpilot と一致
* `ABSACT` の立ち上がりが、4 輪速が個別に瞬断する区間とちょうど一致

結果、**33 時間で ABS 作動 11 件 (0.33 件/時)**。`VSCACT` は 0 件だった。

0x220 (TRCACT / VDMACT) は車両によって流れていないものがある。
0x226 は復号率 99.8% で安定して取れる。

comma2k19 の RAV4 2017 には 0x226 自体が存在しない (BRAKE_MODULE が 0x224)。
**このデータセットでは ABS 作動を判定できない。**

## 12. 信号品質について分かったこと

### 輪速のばらつきは平滑化しないと使えない

生の `ws_spread_mps` は 1 サンプルごとの符号反転率が **62〜67%** (白色雑音なら 50%)。
高周波ノイズが支配的で、平滑化せずに閾値を置くとノイズの尖りだけを拾う。

実際、平滑化前の実装では comma2k19 で `wheel_speed_anomaly` が 16 件出たが、
中身を見るといずれも隣り合うサンプルでばらつきが 0.04 → 0.70 → 0.09 と
飛び跳ねているだけで、持続していなかった。`merge_gap_s` が離れた単発を
1 件に糊付けして継続時間の条件を通していた。

0.3 秒平滑化すると、超過の最大が **1.31 → 0.27 m/s** に落ちる (comma2k19 全体)。

| 平滑化 | p99   | p99.9 | 最大  | >0.4 の割合 |
| ------ | ----: | ----: | ----: | ----------: |
| なし   | 0.190 | 0.445 | 1.305 | 0.145%      |
| 0.15 s | 0.118 | 0.190 | 0.443 | 0.0015%     |
| 0.30 s | 0.098 | 0.158 | 0.270 | 0%          |

対策は 2 つ入れた。輪速を 0.3 秒平滑化してから使うこと、
`wheel_speed_anomaly` の `merge_gap_s` を 1.0 → 0.3 秒に下げること。

結果として **196 セグメントでも comma2k19 でも 0 件**。
超過の最大は 0.42 m/s で閾値 0.4 をかろうじて超えるが、
裏付け (加減速・ヨー乖離・ABS) が取れていない。
この信号品質では「輪速の異常は無い」と言えるところまでは確かめられた。

### ヨー残差の σ は「モデルが成り立つ領域」でしか意味を持たない

単軌道モデルは定常状態のモデルなので、旋回の入口・出口では実測が遅れて残差が出る。
196 セグメントで測った残差の標準偏差は、領域の取り方で 1.7 倍変わる。

| 領域                              | n       | 標準偏差 | \|残差\| p99.9 | 最大  |
| --------------------------------- | ------: | -------: | ---------------: | ----: |
| 全体                              | 196,613 | 0.663    | 5.858            | 10.89 |
| v > 10 m/s                        | 171,423 | 0.449    | 2.061            |  3.78 |
| v > 10 かつ 正味方位変化 < 15 deg | 160,629 | **0.392**| 1.480            |  2.41 |

15 セグメントの高速巡航で当てはめた 0.359 は、3 番目の領域の 0.392 とほぼ一致する。
**当てはめは正しく、領域の指定が抜けていた。**

gate を付ける前は 6σ 超えが全サンプルの 1.33% に達し、
発火した 6 件はすべて正味方位変化 33〜87 度の**通常の旋回**だった。
gate (v > 10 かつ正味方位変化 < 15 deg) を入れると 6σ 超えは 0.002%、
最大でも 6.7σ になり、検出は 0 件になる。
`hard_steer` / `lateral_accel` と同じ扱いにそろえた。

### アクセル開度は 3 台に 1 台でしか読めない

`0x2C1 GAS_PEDAL` の復号率は **34.7%**。車両によってメッセージ自体が流れていない。
アクセル急 OFF → 制動の判定 (`panic_brake_pedal`) は、
台数を増やしてもこの車種の 3 分の 1 しかカバーできない。
縦加速度で代用する `panic_brake` を残してあるのはこのため。

### 制動の強さに上限がある

前後加速度の最小は -4.35 m/s²、車両報告の GVC でも -4.64 m/s² (0.47 g)。
comma2k19 の 0.45 g とほぼ同じで、乾燥路のタイヤ限界 0.8〜1.0 g には遠い。
ABS が 3.3 時間で一度も作動しないのは、ビット位置の誤りではなく
**作動しうる制動が含まれていない**ため。
