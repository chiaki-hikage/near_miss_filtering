# 処理フロー — CAN + 映像による自動抽出パイプライン

走行データからヒヤリハット候補を絞り込み、最後に映像 AI (VLM) で確認する。
この文書は**現在の実装の動き**を説明する。閾値の根拠は
[event_detection_spec.md](event_detection_spec.md)、入出力の形は
[io_spec.md](io_spec.md) を見ること。

---

## 1. 全体像

```
入力データ            comma2k19 / commaCarSegments (rlog.zst) / KIT MSDM
    |
    v
CAN 前処理 (L0)       生 CAN の復号 -> 正規化車両信号
    |
    v
L1 軽量フィルタ        生 CAN の 2 秒窓 max/min だけで走行時間を絞る
    |                 通過率 5.8% / 候補を含む 60 秒 segment 45%
    v
L2 特徴量生成          20 Hz グリッドへ再サンプル -> 平滑化 -> 特徴量
    |
    v
L3 イベント判定        24 種の閾値・共起・系列ルール
    |
    v
候補統合・優先度付け    イベントを時間方向にまとめ、severity と優先度規則で絞る
    |
    v
動画切り出し           候補の時刻からフレームを JPEG に展開
    |
    v
VLM / 映像 AI 判定     構造化出力で risky / hazard_type / evidence を得る
    |
    v
最終出力              候補 CSV + VLM 判定 JSONL + 採点結果
```

---

## 2. L1 / L2 / L3 の役割の違い

**3 つは目的が違う。同じ量を見ているのではない。**

| | L1 | L2 | L3 |
|---|---|---|---|
| **目的** | 走行時間を捨てる | 判定できる量を作る | 事象を特定する |
| **入力** | 生 CAN のサンプル | 生 CAN のサンプル | 20 Hz グリッドの特徴量 |
| **時間の単位** | 2 秒窓 | 20 Hz サンプル | 継続時間つきの区間 |
| **使う量** | `ax` / `ay` / 車速 / 安全系フラグ | 全チャネル + レーダ | 特徴量 24 種のルール |
| **平滑化・微分** | **しない** | する | (L2 の結果を使う) |
| **チャネル間の時刻同期** | **しない** | する (共通グリッド) | (L2 の結果を使う) |
| **落とすもの** | 走行時間の 94% | 落とさない | 事象でない時間 |
| **実装** | `src/near_miss/l1.py` | `signals.py` + `features.py` | `detectors.py` |

**L1 は「捨てる」ための段で、L2 は「作る」ための段。** L1 が軽いのは、
後段の重い処理 (復号・再サンプル・特徴量生成) を走らせる前に置くため。
L1 で平滑化や時刻同期をすると、L2 と同じコストがかかって意味が無くなる。

**L2 は絞り込まない。** 特徴量を作るだけで、ここで候補を落とすことはしない。

## 3. 各ステップ

### 3.1 入力データ

| 目的 | 主な処理 | 主な入力 | 主な出力 |
|---|---|---|---|
| 走行ログを読める形にする | データセット固有の読み出し | `rlog.zst` / `raw_can` | `SegmentData` |

対象は 3 つ。いずれも **CAN のみを特徴抽出に使う**。映像は VLM 段と目視確認にだけ使う。

* **comma2k19** — Toyota RAV4 2017。映像あり。人手ラベル 100 件つき
* **commaCarSegments** — Toyota 4 車種 (RAV4 TSS2 / Corolla TSS2 / Prius / Highlander TSS2)。映像なし
* **KIT MSDM** — 横滑りフィルタの検証用。β の実測がある閉鎖路データ

データセットの差は `src/near_miss/sources.py` の `SegmentSource` に閉じ込めてある。
`features.py` 以降はデータセットも車種も知らない。

**次工程との関係**: 正規化された `SegmentData` を L1 と L2 の両方に渡す。

### 3.2 CAN 前処理 (L0)

| 目的 | 主な処理 | 主な入力 | 主な出力 |
|---|---|---|---|
| 車種依存を検出側に持ち込まない | DBC 定義によるビット抽出と符号補正 | 生 CAN フレーム | チャネル辞書 (時刻 + 値) |

```
生 CAN → RawCanFrames → 正規化車両信号 (SegmentData) → 一様グリッド → 特徴量 → 検出
         ^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^^^^^^^^^
         データセット固有  車種設定 (configs/vehicles/*.yaml) が決める
```

**加速度センサの符号は個体ごとに違う。** 同じ車種キーでも `accel_x` / `accel_y`
の向きが逆の車両がある (Highlander TSS2 は 33 台中 21 台)。`ax` と `ay` は必ず
一緒に反転する。判定は `scripts/calibrate_accel_sign.py` が行い、結果を車種設定の
`calibration.accel_sign` から読む。

### 3.3 L1 軽量フィルタ

| 目的 | 主な処理 | 主な入力 | 主な出力 |
|---|---|---|---|
| 後段に渡す走行時間を数 % まで落とす | 2 秒窓ごとの max/min と固定閾値 | 生 CAN の `ax` / `ay` / 車速 / 安全系フラグ | 窓ごとの通過フラグ |

**固定条件 (基本候補、`src/near_miss/l1.py` の `BASE`)**

```
v >= 5 m/s かつ (ax <= -2.5 m/s^2 または |ay| >= 2.0 m/s^2)
```

**閾値は車種ごとに調整しない。** 調整すると「その車種の分布に合わせただけ」に
なり、別の車種へ持っていけない。

**安全系フラグが立った窓は速度・加速度に関係なく無条件で通す。**

* 無条件通過: `abs_active_flag` / `vsc_active_flag` / `precollision_active` /
  `slip_warn` (値 4 のみ)
* 数えるだけ: `tc_disabled` (切られている状態であって作動ではない) /
  `abs_fault` (故障であって作動ではない)

**なぜ無条件通過にするか。** フラグが立つ窓は全体の 0.02〜0.05% しかなく、
通過率への影響は +0.01 ポイント以下でコストがほぼゼロ。一方で外すと
`activation_only` の保持が 100% → 51%、`high_evidence` が 99% → 83% まで落ちる。
低速や短時間の ABS 作動は運動量の条件に掛からないため、フラグでしか拾えない。

**なぜ 2 秒窓か。** 車速と `ax` は別のアドレス (0x0B4 / 0x024) から別々の時刻で
届く。サンプル単位で判定するには時刻結合 (as-of join) が要る。2 秒窓で各チャネルを
独立に集約してから列同士を比べれば結合が要らない。窓 ID は `floor(t / 2)` という
単なる列式になる。

**取れないもの**: 自車が反応していない前方接近事象。自車の運動しか見ないので
原理的に拾えない。前方接近系 (`cut_in_candidate` / `short_thw` / `low_ttc`) の
L1 保持率は 8〜30% にとどまる。

詳細と根拠は [l1_filter.md](l1_filter.md)。

**次工程との関係**: 通過した窓に重なる区間だけを L2 以降の対象にする。

### 3.4 L2 特徴量生成

| 目的 | 主な処理 | 主な入力 | 主な出力 |
|---|---|---|---|
| 判定に使える量を作る | 再サンプル → 平滑化 → 特徴量 | チャネル辞書 + レーダ | 20 Hz の `DataFrame` |

**再サンプル (20 Hz)。** CAN の受信時刻は最小 0.2 ms まで詰まることがあり、
生の時刻で微分すると量子化ノイズが 100 m/s² 規模まで増幅される。受信間隔が
0.5 秒を超える箇所は欠測として品質フラグを立てる。平滑化の端の影響を除くため、
両端 0.6 秒を捨てる。

**平滑化 (対称移動平均)。** 車速 0.25 s / 舵角 0.15 s / 縦加速度 0.25 s /
輪速 0.3 s。輪速は生のばらつきの符号反転率が 62〜67% (白色雑音なら 50%) で
高周波ノイズが支配的なため、平滑化せずに閾値を置くとノイズの尖りだけを拾う。

**作る特徴量**は約 50 列。主なものは次のとおり。

* 運動量 — `ax_mps2` / `ay_kin_mps2` / `ay_can_mps2` / `jerk_mps3` / `yaw_rate_dps`
* 操舵 — `steer_rate_dps` / `steer_reversals` / `net_heading_win_deg`
* 輪速 — `ws_spread_mps` / `ws_spread_excess_mps` / `wheel_decel_mps2`
* 車間 — `thw_s` / `ttc_s` / `lead_distance_m` / `lead_vrel_mps`
* 物理整合 — `yaw_residual_sigma` / `beta_model_deg`
* 派生フラグ — `weave_active` / `s_evasion_active` / `cut_in_active` など

**横加速度は 2 系統ある。** `ay_can_mps2` は CAN の横 G センサ、`ay_kin_mps2` は
`車速 × ヨーレート` の運動学値。**直進制動中に CAN 側が見かけの横 G を出す**ことが
あるため (Highlander で 2.90 件/h)、横方向の判定では両方を見る。

**`yaw_residual_sigma` は車両諸元 (ステアリングギヤ比・アンダーステア勾配) が
要る。** 諸元が取れていない車種では計算されない。

**次工程との関係**: この `DataFrame` が L3 の唯一の入力になる。

### 3.5 L3 イベント判定

| 目的 | 主な処理 | 主な入力 | 主な出力 |
|---|---|---|---|
| 事象の区間を特定する | 閾値・共起・系列の 4 種のルール | 20 Hz の `DataFrame` | `events.csv` |

24 種のイベントを 4 つの判定方式で検出する。

| 方式 | 意味 | 例 |
|---|---|---|
| `threshold` | 判定量が閾値を継続時間だけ超える | `hard_brake` / `low_ttc` |
| `rising` | フラグが 0.5 を上向きに跨ぐ | `abs_active` / `aeb_active` |
| `agreement` | 複数条件の AND (時間ずれを許容) | `hard_steer` |
| `cooccurrence` / `sequence` | 他イベントとの共起・前後関係 | `risky_lane_change` / `brake_after_evasion` |

**ゲート**は「その条件下では判定しない」区間を外す。`hard_steer` と
`lateral_accel` は `net_heading_win_deg < 15` のゲートを持つ。回避操作は元の
向きへ戻るが、カーブは戻らない。大きさだけではカーブと回避を分離できない。

**段 (stage)**: レーダや安全系フラグを使うものは段 2。CAN の基本信号だけで
決まるものは段 1。段 1 だけで動かすこともできる。

閾値の一覧は [event_detection_spec.md](event_detection_spec.md)。
**閾値はすべて `configs/detection.yaml` にある。コードには埋め込まない。**

**次工程との関係**: イベントを候補統合に渡す。

### 3.6 候補統合・優先度付け

| 目的 | 主な処理 | 主な入力 | 主な出力 |
|---|---|---|---|
| 確認する単位にまとめ、見る順を決める | 時間方向の結合 → severity → 優先度規則 | `events.csv` | `candidates.csv` |

**統合 (`build_candidates`)**

1. 各イベントの前後に余白 2 秒を付ける
2. 間隔が 2 秒以内のものを 1 つの候補にまとめる
3. severity を足し合わせる。**同じ種類が複数あっても最も強い 1 件だけ**を足す
4. 種類が 2 つ以上あれば共起ボーナス 0.5 を種類数 − 1 だけ加える

1 イベントの severity には上限 3 を置く。1 つの極端な値で候補全体が上位に来ないようにするため。

**優先度規則 (`configs/priority.yaml`)**

候補生成そのものは変えず、**候補の集計値だけで絞る**。severity では表現
できない判別要素 (車間距離そのもの、複数量の連言) をここで扱う。

* `always` — 無条件で採用。車両自身が危険と判断した瞬間で、こちらが閾値を
  決める余地がない (`abs_active_flag` / `vsc_active_flag` / `slip_warn` ≥ 3.5 /
  `precollision_active`)
* `rules` — OR で評価。`require_types` に挙げた種別を含む候補にだけ条件を課す

**次工程との関係**: 採用された候補の時刻が、動画切り出しの入力になる。

### 3.7 動画切り出し

| 目的 | 主な処理 | 主な入力 | 主な出力 |
|---|---|---|---|
| VLM に渡す画像を用意する | ffmpeg でセグメントを JPEG に展開 | `video.hevc` + 候補時刻 | フレームキャッシュ |

**セグメントを丸ごと展開してキャッシュする。** 候補ごとに切り出すと同じ
セグメントを何度もデコードすることになる。

**60 秒セグメントの境界をまたぐ候補がある。** 評価時刻が手元にあっても、
その 4 秒前が別セグメントにあって欠けていれば入力を組み立てられない。
`windows.py` が必要なセグメントの有無を先に確かめる。

`hwaccel=True` で NVDEC を使う。推論機は vCPU が少ないことが多く、デコードを
GPU へ逃がして CPU を空けるため。

**次工程との関係**: フレームの並びと特徴量の要約が VLM のリクエストになる。

### 3.8 VLM / 映像 AI 判定

| 目的 | 主な処理 | 主な入力 | 主な出力 |
|---|---|---|---|
| 候補が本当にヒヤリハットかを確認する | 構造化出力つきの VLM 推論 | 画像 + 特徴量要約 | 判定 JSONL |

**2 つのモードがある。**

* **モード A (clip)** — 候補区間を一括で見て 1 回判定する
* **モード B (online)** — 0.5 秒ごとに前へ進みながら逐次判定する。
  過去だけを見て判定するため、事象の onset を測れる

**制約**

* **人手ラベル (`risky`) はリクエストに入れない。** 採点時に `event_id` で
  突き合わせる
* **schema と prompt は固定する。** 変えると条件間の比較が成立しない
* **`runner.py` 以外は `vllm` を import しない。** 入力生成と採点を GPU の無い
  機械でも動かせるようにするため
* **モデルを差し替えても入力生成・prompt・schema・評価は変えない。** 変わってよい
  のは重み・chat template・視覚トークン化だけで、`adapters.py` が吸収する
* **`--backend echo`** は推論をせずに全経路を通す試験用。**推論ではない**

**次工程との関係**: 判定 JSONL を採点に渡す。

### 3.9 最終出力・採点

| 目的 | 主な処理 | 主な入力 | 主な出力 |
|---|---|---|---|
| 判定の質を人手ラベルで測る | `event_id` で突き合わせ | 判定 JSONL + `labels.csv` | 採点結果 + digest |

**標本が小さいため、性能の確定はしない。**

* 指標は必ず件数を併記する。百分率だけを出さない
* 信頼区間は参考値として出す。結論の根拠にしない
* negative は**人手確認済みに限る**。「フィルタで落ちた = negative」とは扱わない

# L3 まで (comma2k19)

uv run python scripts/build_vlm_inputs.py  ...

## 5. 設計上の約束

* **閾値をコードに埋め込まない。** すべて `configs/` に置く。閾値を変えた実行は
  `config_hash` が変わるので出力側で区別できる
* **元データを上書きしない。** 中間結果と抽出理由を残す
* **欠測を安易に補完しない。** 判定できないことを「条件を満たす」にしない
* **層を跨がない。** `features.py` 以降はデータセットも車種も知らない。
  データセットを足すときは `sources.py` に `SegmentSource` を返す関数を 1 つ書く
