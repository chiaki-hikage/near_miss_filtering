# ZOD Sequences full の取得計画と解析の方針

2026-11-12。ZOD を横風の外乱推定の主なデータセットとして進める方針 (ユーザーの判断) に沿った計画。**取得はユーザーが行う** (`docs/zod_download.md`)。Claude Code は Dropbox の共有リンクを読み取らず、ダウンロードも実行しない。

根拠: `docs/zod_signals.md` (信号の単位・座標系・同期)、`docs/zod_drive_validation.md` (走行全体の車両データ・モデルの確かめ)。

---

## 1. 取得の対象 (構成 A)

```bash
zod download --subset sequences --version full \
    --output-dir ~/work/near_miss_filtering/raw_data/zod \
    --no-images --no-blur --no-lidar --no-radar --no-annotations
```

公式の CLI (`zod` 0.8.0、`zod/cli/download.py` の `_filter_entry`) は、Dropbox の `sequences` フォルダのファイルを名前で振り分ける。

| ファイル名に含まれる語 | 構成 A で |
|---|---|
| `vehicle_data`, `oxts`, `infos` | 取る |
| `images` (`blur`, `dnat` を含む), `lidar`, `radar`, `annotations` | 取らない |
| `mini` | 取らない (`--version full` では除く) |
| **上のどの語も含まないもの** | **取る** (除外の条件に当たらないため。何があるかは dry run と Dropbox の一覧で確かめる) |

`calibration.json`, `metadata.json`, `ego_motion.json`, `trainval-sequences-full.json` が `infos` のアーカイブに入っているかは、公開資料では分からない。取得後の `zod verify` で `GENERAL` の項目が 100% になるかで確かめる。

## 2. 容量

### 2.1 1 シーケンスあたりの実測 (mini、2 シーケンス)

| 中身 | 展開後 | gzip で圧縮した大きさ (参考) | 備考 |
|---|---|---|---|
| `oxts.hdf5` | 8.70 MB | 1.12〜1.18 MB | HDF5 の中は圧縮なし。50 s で固定の長さ |
| `vehicle_data.hdf5` | 5.09 MB (55 分) / 8.46 MB (98 分) | 4.85 / 8.13 MB | **HDF5 の中で gzip 済み**で、ほとんど縮まない。**走行全体が入っているので、走行の長さに比例** (約 0.09 MB / 分) |
| `ego_motion.json` + `calibration.json` + `metadata.json` | 0.19 MB | 約 0.08 MB | |
| infos (`trainval-sequences-*.json`) | 63 KB / シーケンス | 4 KB / シーケンス | カメラ・ライダーのファイル名の一覧を含む |
| 合計 | **14.0〜17.4 MB** | 約 6.1〜9.4 MB | |

mini のアーカイブ (`mini.tar.gz`) は 1.43 GB で、展開後の 2.08 GB の 69% だった (ライダー・カメラを含む全体の値)。

### 2.2 full (1,473 シーケンス) の見込み

**推定。** 2 シーケンスの実測からの掛け算で、full のアーカイブの形式・分け方・大きさは Dropbox の一覧を見るまで分からない。

| | 下限の目安 | 中央の目安 | 上限の目安 | 前提 |
|---|---|---|---|---|
| 展開後 | 18 GB | 23 GB | 37 GB | 車両データの走行の長さ: 下限 30 分、中央 75 分 (mini の 2 走行の平均)、上限 180 分 (1 走行が長い場合)。OXTS と json は固定 (8.9 MB × 1,473 = 13 GB) |
| アーカイブ (tar.gz、mini と同じ形式の場合) | 6 GB | 11 GB | 26 GB | OXTS は 1/7.5 に、車両データはほぼそのまま |
| アーカイブ (圧縮なしの tar の場合) | 18 GB | 23 GB | 37 GB | 展開後と同じ |
| **作業中の最大 (アーカイブ + 展開後が両方ある)** | 24 GB | 34〜46 GB | **74 GB** | CLI の既定 (`--rm` なし)。展開は各ファイルの取得の後に行われ、別の一時ファイルは作らない (CLI のソースで確認)。取得中のファイルはアーカイブそのもので、途中で止まっても大きさは増えない |
| 確かめた後 (アーカイブを消した場合) | 18 GB | 23 GB | 37 GB | 消すかはユーザーが `du` を見て決める (`docs/zod_download.md` 手順 7) |

- 前回の「約 20 GB」は展開後の中央の目安にあたる。**作業中には、アーカイブの形式によって最大で約 2 倍 (上限の目安で 74 GB) が要る**
- 同じ走行から複数のシーケンスが選ばれていれば、各シーケンスの `vehicle_data.hdf5` に同じ走行全体が入る (mini の 2 シーケンスは別の走行だった)。その分は上の掛け算に含まれている (1 シーケンス 1 ファイルとして数えた)
- 空き容量: 412 GB (2026-11-12、mini 取得後)。上限の目安でも収まる
- 取得の前に、Dropbox の一覧 (手順 3) でアーカイブの名前と大きさを確かめ、この表を実際の値で置き換える

## 4. 解析の方針 (full を取得できたら)

コードは `scripts/zod/`、設定は `configs/zod/`、出力は `out/zod/<段階>/full/`。comma のコード・共通ライブラリ (`src/near_miss/`) とは共通化しない (今回の方針)。

### 段階 1: 可用性の調査

全シーケンスについて (`inspect_signals.py` と `drive_validation.py` の一覧の部分を全件に):
- 車両 (`collection_car`)・国・日時 (UTC と現地)・位置
- 走行全体の長さ、車両データの途切れ、衛星測位の欠け・HDOP
- OXTS の 50 s: 測位の状態 (`stdDevPos*`, `stdDevVel*`, `positionMode`)。**横滑り角を使えるシーケンス (速度の標準偏差が小さいもの) の割合**
- 同じ走行を共有するシーケンスの組 (車両データの開始時刻と車両で判断)。走行全体の車両データを重ねて数えないため
- 車両ごとの舵角のゼロ点 (§段階 3 の前提)

### 段階 2: 候補区間の抽出

| 区間 | 条件 (初期値。`configs/zod/` に置く) | 使う信号 |
|---|---|---|
| OXTS の 50 s のうち高速・直進 | 速さ 80 km/h 超、\|r\| < 1 deg/s、方向指示器の前後 3 s を除く | OXTS、車両データ |
| 走行全体の高速・直進 | 速さ 80 km/h 超、\|δsw − c\| < 3 deg、方向指示器の前後を除く、途切れの前後 2 s を除く | 車両データ |
| 除くもの | 車線変更 (方向指示器)、低速、途切れの近く、OXTS が RTK でない区間 (横滑り角を使う場合) | |

### 段階 3: 外乱の候補の検出

1. **車両ごとのモデル**: 同じ車両の多くのシーケンスの OXTS の 50 s で、δsw = a·(r/v) + b·(v·r) + c と、舵角の遅れ (0〜0.1 s) を決める。遅れの値と a, b, c は、**評価に使わないシーケンスで決める** (シーケンス単位、または日付単位の分割)
2. **ヨー残差** Δr = r − r_pred (OXTS の 50 s)。車両 × 速さごとの正常の分布 (多くのシーケンスの分位点) に対する外れ方で表す
3. **補助の指標**: 横滑り角 (RTK のときだけ)、操舵トルク (当て舵)、0.2〜2 Hz の横加速度の残差 (ロールの補正つき)。OXTS と車両 IMU の横加速度が 2 Hz 以下で一致しているか (センサの作り物を除く)
4. **走行全体**: 車両データだけの残差で時間帯を絞る (ふるい分け)。この結果だけで外乱とはしない (`docs/zod_drive_validation.md` §1.5)
5. 外乱の候補の形: 「舵角の変化を伴わずにヨー・横滑りが変わり、その後に当て舵 (トルク) が続く」。comma の検討 (`docs/crosswind_civic_feasibility.md`) と同じ考え方

### 段階 4: 気象との照合

具体的な手順と、mini での確かめ (観測所の近さ・時間分解能・観測所どうしの一致・検出限界) は `docs/zod_weather_poc.md` §6。

- シーケンスの UTC と位置 (OXTS、または車両データの衛星測位) で、近くの気象観測所の風速・突風・風向を引く。観測所のデータの取得元と利用条件は、取得の前に確かめる (`docs/crosswind_wind_data.md` の考え方)
- 強風のシーケンスと弱風のシーケンスで、段階 3 の指標の分布を比べる (群としての差を見る)。風向と進行方向から横風の成分を求める
- **国・月だけを根拠に強風があったとは推定しない**

### 段階 5: 上位の候補の映像による確かめ

- カメラがあるのは各シーケンスの 20 s だけ。候補がその中にあれば、前方カメラ (構成 B の一部) を取る。full の構成 B は全部で約 110〜120 GB (推定) なので、アーカイブの分け方を見てから取り方を決める
- 映像では、候補の時刻の道路の形・車線変更・路面・周りの車を確かめ、外乱の説明がつくかを見る。映像だけで風を確定しない (PhysicalAI-AV の確認と同じ方針)

### 危険度と、横風が原因である可能性を分ける

2 つは別の指標にし、1 つの点数にまとめない。

| | 危険度 (ヒヤリハットとしての深刻さ) | 横風が原因である可能性 |
|---|---|---|
| 問い | 車がどれだけ予定の進路から外れ、運転者がどれだけ大きく補正したか | その横方向の動きを、風で説明するのがどれだけもっともらしいか |
| 指標の候補 | 横方向のずれ (OXTS の位置と、前後から求めた予定の進路の差)、ヨー・横滑りの大きさ、当て舵の大きさと速さ (舵角速度・トルク)、速さ。車線の中の位置は信号に無いので、映像の確認か、注釈 (中央の 1 フレームの車線) の範囲で補う | ヨー残差の外れ方 (舵角で説明できない分)、操舵より先に動きが出ているか、横滑りの向き、気象の観測の風速・突風と横風の成分、ほかの原因 (車線変更・カーブの入口・路面・追い越しのトラック) の有無 |
| 例 | 大きく補正したが、原因は車線変更だった → 危険度は高く、横風の可能性は低い | 小さなヨーの外乱が強風の時間に出た → 横風の可能性はあるが、危険度は低い |

- 横風の正解ラベルは無い。「横風の可能性」は、気象の照合と映像の確認で上げ下げする判断材料で、確定ではない
- 出力では 2 つの指標を別の列にし、それぞれの根拠 (どの信号・どの閾値) を残す (CLAUDE.md の「判定根拠が追跡できる実装」)
