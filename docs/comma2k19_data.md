# comma2k19 のデータと信号
> データセット間の比較は [datasets.md](datasets.md) にまとめてある。

本プロジェクトで扱う範囲に絞った整理。単位と構成はデータセットの README に
記載された定義に従い、記載の無いものは実測で確かめた値を使う。
信号ごとの符号・スケールの検証結果は [signals_rav4.md](signals_rav4.md) にある。
別のデータセット (commaCarSegments) を扱う場合は
[comma_car_segments.md](comma_car_segments.md) を参照。読み出し層より下は共通で、
データセット固有の処理は `src/near_miss/io/` の中だけに閉じている。

## 1. データセットの構成

| 項目 | 内容 |
|---|---|
| 総量 | 約 33 時間 / 2019 セグメント / 約 100 GB |
| 1 セグメント | 60 秒 (実測でも全 64 セグメントが 60.0 秒) |
| 走行路 | カリフォルニア 280 号線の約 20 km 区間。高速道路のみ |
| 車両 | Chunk 1-2 = Toyota RAV4 (`b0c9d2329ad1606b`) / Chunk 3-10 = Honda Civic (`99c94dc769b5d96e`) |
| 記録機器 | comma EON (カメラ・GPS・9 軸 IMU) + grey panda (CAN 傍受) |

```
Chunk_N/
+-- <dongle_id>|<開始日時>/          ドライブ
    +-- <セグメント番号>/            60 秒
        +-- preview.png              先頭フレーム       488 KB
        +-- video.hevc               映像 20 Hz          36 MB
        +-- raw_log.bz2              capnp 生ログ       6.6 MB
        +-- processed_log/           numpy 配列         6.8 MB
        +-- global_pose/             カメラの絶対姿勢   136 KB
```

容量の約 7 割が映像。CAN しか使わない場合、`processed_log/CAN` だけなら
1 セグメントあたり 5.1 MB (うち `raw_can` が 4.1 MB) で済む。

セグメント番号は連番とは限らない。Hugging Face の demo split は
1 ドライブから数本ずつ抜き出されており、番号が飛ぶ。連結処理は
連番になっている範囲だけをまとめ、欠番を跨がない。

## 2. raw と processed の区別

**この区別は「加工の有無」であって「品質の良し悪し」ではない。**
`processed_log` も平滑化やリサンプルはされていない。物理値に直して
配列に並べただけで、受信時刻のばらつきはそのまま残っている。

| 種別 | 対象 | 内容 |
|---|---|---|
| raw | `raw_log.bz2` | openpilot の capnp ログ全体。読むには openpilot-tools が要る |
| raw | `processed_log/CAN/raw_can` | CAN フレームそのもの (`t` / `address` / `data` / `src`)。復号は利用側の責任 |
| raw | `processed_log/GNSS/raw_gnss_*` | 衛星ごとの疑似距離。laika 向け |
| processed | `processed_log/CAN/{speed,steering_angle,wheel_speed,radar}` | 物理値に復号済み。単位は README 記載 |
| processed | `processed_log/IMU/*` | Android の校正を適用済み。`gyro_uncalibrated` は未校正 |
| processed | `processed_log/GNSS/live_gnss_*` | 測位解 |
| processed | `global_pose/*` | カメラの絶対位置・姿勢・速度 (ECEF) |

`processed_log/CAN` に出ている 4 種類は、`raw_can` から復号できる内容の
一部を先に取り出したもの。両方に同じ情報がある信号は `processed_log` 側を使う
(単位が README で保証されているため)。

## 3. 信号ごとの単位と周期

実測は demo split 64 セグメント (RAV4) による。

### processed_log/CAN

| 信号 | 単位 | 平均レート | 備考 |
|---|---|---|---|
| `speed` | m/s | 82.9 Hz | 車速。分解能は元の CAN で 0.01 km/h |
| `steering_angle` | deg | 82.9 Hz | ステアリングホイール角。舵角ではない |
| `wheel_speed` | m/s ×4 | 82.9 Hz | `[前左, 前右, 後左, 後右]`。分解能 0.01 km/h |
| `radar` | 下記 | 123.6 Hz | 全トラック合算。1 行が 1 トラックの 1 観測 |

`radar` の列は `[前方距離 m, 左方距離 m, 相対速度 m/s, nan, nan, address, new_track]`。
address 528-541 の 14 トラック。相対速度は**負が接近**
(距離の時間変化率との回帰係数 +0.988、r = +0.998 で実測確認)。

### raw_can から復号する信号 (Toyota RAV4)

address は 165 種類 (全 64 セグメントで一定)。本プロジェクトが使うのは以下。
ビット定義は `opendbc` の Toyota DBC 由来、符号は実測で補正している。

| 信号 | CAN ID | 単位 | レート | 状態 |
|---|---|---|---|---|
| `ACCEL_X` | 36 (0x024) | m/s² | 82.9 Hz | 符号反転を補正済。**スケール未確定** |
| `ACCEL_Y` | 36 | m/s² | 82.9 Hz | 符号反転を補正済。**スケール未確定** |
| `YAW_RATE` | 36 | deg/s | 82.9 Hz | 符号・スケールとも検証済 (回帰係数 0.988) |
| `BRAKE_PRESSED` | 548 (0x224) | 0/1 | 41.5 Hz | **バス 0 に限ること**。検証済 |
| `FABS` | 800 (0x320) | 0/1 | 20.7 Hz | ABS 作動 |
| `DECEL_FLAG` | 800 | 0/1 | 20.7 Hz | 強い減速で立つ。意味は未確定 |
| `GVC` | 800 | m/s² | 20.7 Hz | 車両が算出した前後 G。車速微分と r = +0.98 / 傾き 0.943 |
| `GAS_PEDAL` | 705 (0x2C1) | % | 31.5 Hz | アクセル開度。0〜100%、25.5% の時間で > 0 |
| `src` | — | — | — | 下位ビットがバス番号、0x80 が立つとデバイス送信フレーム |

`GVC` と `GAS_PEDAL` は commaCarSegments を扱う過程で opendbc に定義を見つけたもの。
comma2k19 の RAV4 でも同じ位置にあることを確かめて復号対象に足したが、
現時点で検出条件には使っていない。

#### 復号経路の突き合わせ用

commaCarSegments には `processed_log` が無く、車速・舵角・輪速も生 CAN から作る。
その経路が正しいことを確かめるため、comma2k19 側でも同じ定義で復号し直した値を
別チャネル名 (`*_can_*`) で持ち、配布値と比べている
(`scripts/check_signal_parity.py`)。

| 主系列 | 生 CAN から復号 | 傾き | rmse |
|---|---|---|---|
| `speed` | 4 輪速の平均 | 1.00000 | 0.0002 m/s |
| `speed` | 0x0B4 SPEED | 1.02130 | 0.57 m/s |
| `wheel_speed` ×4 | 0x0AA | 1.00000 | 0.0005 m/s |
| `steering_angle` | 0x25 本体 + 端数 | 1.00000 | 0.0012 deg |

**配布されている `speed` は 4 輪速の平均そのもの**で、0x0B4 の SPEED は
2.13% 高い表示車速だった。表示車速の較正は車種ごとに違うため、主系列には使わない。

`src` は必ず見る。下記 4.6 のとおり、同じアドレスが複数のバスに
別の内容で流れていることがある。

### 使わないもの

`IMU` / `GNSS` / `video.hevc` / `raw_log.bz2` は、現在の「CAN のみ」という
範囲では読まない。`preview.png` と `video.hevc` は目視確認に使う。

`global_pose` は**検証にのみ**使う。CAN 信号のスケールを外部基準と
突き合わせる用途で、特徴量には入れない (YAW_RATE のスケール検証がこれにあたる)。

`BRAKE_PRESSURE` (548, bit 43) はビット位置が誤っており無効のまま。
`ESP_CONTROL` (0x3B7) はビット定義が未取得。理由は
[signals_rav4.md](signals_rav4.md) 2 章。

## 4. 取り扱い上の注意

### 4.1 時刻はデバイスの boot time

絶対時刻ではない。同一ドライブ内では連続だが、ドライブを跨ぐと不連続になる。
UTC が要るときは `GNSS/live_gnss_*` の `utc_timestamp` を使う。

### 4.2 受信間隔が揃っていない — 生の時刻で微分してはいけない

82.9 Hz の公称に対し、実測の間隔は次のとおり。

```
speed の時刻差分 318,252 件中
  dt == 0 が 25 件 (64 セグメント中 10 セグメントに出現)
  dt <  0 は 0 件 (単調非減少ではある)
  dt 最大 0.0344 s
```

輪速の分解能は 0.01 km/h (= 0.0028 m/s)。dt が 0.2 ms まで詰まった箇所で
1 LSB 動くと、見かけの加速度が 15 m/s² を超える。実際に生の時刻で微分した
ところ +180 m/s² まで振れた。**一様グリッド (既定 20 Hz) へ再サンプルしてから
微分する。** これは推奨ではなく前提条件。

### 4.3 欠測を埋めない

受信間隔が `max_gap_s` (既定 0.5 s) を超えた区間は NaN のままにする。
閾値判定は NaN で発火しないため、「条件を満たさなかった」と
「判定できなかった」が下流で区別できる。

demo split での有効サンプル率:

| 特徴量 | 平均 | 最小 | 欠測の理由 |
|---|---|---|---|
| `ax_mps2` / `steer_rate_dps` | 99.7% | 99.7% | 平滑化の端を捨てているため |
| `ay_can_mps2` / `fabs` | 100% | 100% | — |
| `lead_distance_m` | 79.3% | 12.6% | 自車レーンに先行車がいない |
| `thw_s` | 68.3% | 12.6% | 上記 + 低速時は算出しない |
| `ttc_s` | 36.8% | 0% | 接近しているときだけ定義される |

`radar` は先行車が居ない間データが出ない。観測間隔の最大は 12.95 秒だった。
**TTC のカバレッジが 37% しかないのは異常ではなく、定義どおりの挙動。**

### 4.4 60 秒分割でイベントが分断される

急ブレーキがセグメント境界を跨ぐと両側で継続時間の条件を満たさなくなる。
検出の前に、同一ドライブの連番セグメントを時間軸で連結する。

### 4.5 openpilot が動いている

`raw_can/src` の 0x80 ビットが立ったフレームはデバイス送信。
RAV4 では `0x2E4 STEERING_LKA` が 100 Hz、`0x343 ACC_CONTROL` が 43 Hz で
送信されており、**demo split の全 64 セグメントで送信が確認された** (送信フレーム
比率 27.1%)。

ただし openpilot は非作動時も LKA フレームを送り続けるため、
**「送信の有無」では作動を判別できない。** 現在の `op_tx` フラグは全区間で 1 に
張り付いており、識別子として機能していない。作動区間の切り分けは未解決。

手がかりはある。`0x2E4` の先頭 2 バイトのユニーク値を数えると、セグメントによって
64 と 300〜600 にはっきり分かれる。64 はカウンタとチェックサムだけが動く一定指令で、
非作動の可能性が高い。ビット定義を推測せずに切り分けられそうだが、未検証。

### 4.6 同じアドレスが複数のバスに流れる

`raw_can` は全バスのフレームを 1 本の列に混ぜて持っている。`src` を見ずに
アドレスだけで選ぶと、**別のメッセージを同じ信号として復号してしまう**。

1 セグメントの全アドレスを走査したところ、受信フレームで衝突しているのは 5 件
(`0x223` / `0x224` / `0x228` / `0x232` / `0x3D3`)。このうち `0x224` は
本プロジェクトが使う BRAKE_MODULE で、バス 1 側は先頭バイトがローリングカウンタの
別メッセージだった。混ぜて復号すると `BRAKE_PRESSED` が 59 秒間に 149 回
チャタリングする。バスを指定すると 13 回に収まる。

本プロジェクトが使う他のアドレス (`0x024` / `0x0AA` / `0x0B4` / `0x320`) は
いずれもバス 0 単独。詳細は [signals_rav4.md](signals_rav4.md) 1 章。

### 4.7 診断通信は含まれない

address を全走査しても UDS / OBD-II の応答レンジ (0x7xx) は 0 件。
grey panda がバスを傍受しているだけで、スキャンツールが接続されていないため。
「診断情報」に相当するものとして使えるのは以下。

- 車両側の作動フラグ: `0x320 VSC1S07` の DECEL_FLAG (強い減速)。
  ABS (FABS) は 3.1 時間で 1 度も立たず、検証できていない
- openpilot の送信フレーム: `raw_can/src >= 128`
- `raw_log.bz2` の capnp ログ (今回は CAN のみで進めるため対象外)

`ESP_CONTROL` (0x3B7) に TCS / ESC の作動が入っているとされるが、
**64 ビットすべてが固定値**で中身が無い (`VSC1S08` 0x420 も同様)。
ビット定義を入手しても、このデータには介入そのものが記録されていない。

ABS についても同じで、最大減速度が 0.45 g とタイヤ限界に遠く、
車輪のロックが起きていないため作動しえない。詳細は
[signals_rav4.md](signals_rav4.md)。

### 4.8 車線マーカの正解が無い

データセットに車線の位置や本数のラベルは含まれない。`global_pose` から
自車の軌跡は分かるが、それが何車線目なのかは分からない。
このため車線変更は**断定できず、運動の形から候補として拾うだけ**になる
([near_miss_filters.md](near_miss_filters.md) 3 章)。
妥当性を確かめる方法は映像の目視確認しかない。

### 4.9 高速道路のみである

交差点・信号・歩行者・自転車が存在しない。想定できるヒヤリハットは
先行車のカットインや急減速に伴う車間逼迫にほぼ限られる。
市街地を前提とした検出条件をそのまま持ち込まない。
