# L1 軽量フィルタ — 生 CAN だけで走行時間を絞る

確認すべき時間を全走行時間の数 % まで落とす足切り。後段 (特徴量を作る重い処理や
目視) に渡す前に置く。**再現率ではなく通過率を狙って閾値を決める。**

実装

* `scripts/raw_can_filter.py` — 通過率を狙った閾値探索 (comma2k19)
* `scripts/l1_trigger_search.py` — 枝ごとの通過率の配分探索、窓方式と event 方式の比較
* `scripts/l1_round_thresholds.py` — 丸い閾値の総当たりと leave-one-out
* `scripts/l1_apply_ccs.py` — 固定した閾値を commaCarSegments に当てる
* `scripts/l1_branch_contrib.py` — 枝ごとの寄与と ablation (閾値は固定のまま)

---

## 1. 使うもの・使わないもの

**使う。** 安全系フラグ (ABS / VSC / TRC / PCS / 滑り警告) と、生の
`ax` / `ay` / `yaw` / 舵角 / 車速 / 輪速の **2 秒窓の max / min / range**。

**使わない。** 平滑化・微分・チャネル間の時刻同期・派生特徴量。
各チャネルは**自分のタイムスタンプだけ**で窓に振り分けて集計する。

**なぜ 2 秒窓か。** 速度と `ax` は別のアドレス (0x0B4 / 0x024) から別々の時刻で
来る。`v >= 5 かつ ax <= -2.5` をサンプル単位で判定するには時刻結合 (as-of join)
が要る。2 秒窓で各チャネルを独立に集約してから列同士を比べれば結合が要らない。
窓 ID は `floor(t / 2)` という単なる列式になる。

## 2. 対象の切り分け — 前方接近は L1 では取れない

自車の運動しか見ないので、**自車が反応していない接近事象は原理的に拾えない**。
人手ラベルの risky 12 件を実測で 2 つに分けた
(`scripts/l1_trigger_search.py` の `--react-*`、出力 `out/l1_trigger/classification.csv`)。

| 分類 | 件数 | 基準 |
|---|---|---|
| **L1 対象** (自車反応あり) | 9 | ラベル区間で \|ax\| >= 2.0 / \|ay\| >= 2.0 / 舵角の振れ >= 30° のいずれか |
| **L1 対象外** (前方接近主体) | 3 | 上のどれも満たさない |

**種別名では分類できない。** 所見だけでは前方接近に見える 2 件が、実測では
自車が急制動していた (`short_thw` の 1 件は `ax` −6.17 m/s²、`cut_in` の 1 件は
`ax` −3.30 / \|ay\| 3.09)。逆に L1 対象外の 3 件は `ax` −0.5〜−1.2、
\|ay\| 0.5〜0.8、舵角の振れ 1.6〜6.1° と通常走行と区別がつかない。

## 3. 枝の選び方 — ax 減速と ay だけでよい

`ax_decel` / `ax_accel` / `ay` / `yaw` / `steer` の 5 本を独立した OR 条件として
扱い、丸い閾値の総当たりで比べた (comma2k19 Chunk_1 + Chunk_2、6.36 時間)。

| 構成 | 通過率 | L1 対象 risky |
|---|---|---|
| ax減速 −2.0 + ay 2.0 | 4.19% | **9/9** |
| + ax加速 3.0 | 4.41% | 9/9 |
| + yaw 15 | 4.19% | 9/9 |
| + steer 50 | 4.29% | 9/9 |
| + yaw 15 + steer 50 | 4.29% | 9/9 |

**追加した枝はどれも保持を 1 件も増やさず、通過率だけ増やす。**
`yaw 15` は通過率が変わらない = `ay` / `ax` がすでに拾った窓しか拾っていない。
`hard_accel` の L1 対象 risky 1 件も ax 加速枝なしで保持される。

単独枝では届かない (ax減速 −2.0 単独で 7/9、ay 2.0 単独で 5/9)。**2 枝の OR が要る。**

### 固定候補

| 名前 | 条件 |
|---|---|
| 標準 | `v >= 5` かつ (`ax <= -2.0` または `\|ay\| >= 2.0`) |
| 高圧縮 | `v >= 5` かつ (`ax <= -2.5` または `\|ay\| >= 2.0`) |
| 1 段階厳 | `v >= 5` かつ (`ax <= -3.0` または `\|ay\| >= 2.5`) |

いずれも**制御・安全系フラグが立った窓は速度・加速度に関係なく無条件通過**。
TRC 単独の旋回加速も L1 では落とさない (優先度は後段で決める)。

無条件通過にするのは `abs_active_flag` / `vsc_active_flag` /
`precollision_active` / `slip_warn` (値 4 のみ)。
`tc_disabled` (切られている状態であって作動ではない) と `abs_fault` (故障) は
数えるだけで通過条件には使わない。

### 枝ごとの寄与

固定した丸い閾値 (`ax_decel` −2.5 / `ax_accel` +3.0 / `ay` 2.0 / `yaw` 15 /
`steer` 50 / `v_min` 5.0) のまま、枝を 1 本ずつ単独で使ったときの通過率と、
最終 OR (高圧縮) に対する寄与を測った (`scripts/l1_branch_contrib.py`)。
**閾値の再最適化はしていない。**

* **単独通過率** その枝だけで通る 2 秒窓の割合。運動量枝には速度ゲートを掛ける
* **他枝と重複** その枝が通す窓のうち、他のどれかの枝も通す窓の割合
* **最終への寄与** 採用枝は外したときの減少分、非採用枝は足したときの増分

* **`yaw` の重複率は両データセットで 100%。** 15 deg/s を超える窓は 1 つ残らず

* **`steer` は commaCarSegments では単独 3.68% と大きいが、重複 81% で独自分は

* **`flags` は単独 0.03% しか通さない。** 通過率の観点ではコストがほぼゼロ。

  低速の滑りを取りたいなら外す判断もありうる。

## 4. 過適合について

**正例が 9 件しかない。** 連続値で最適化すると、その 9 件にだけ合う閾値が出る。
丸い値の候補に限り、同点なら「通過率が小さい → 枝が少ない」の順に選ぶ。

leave-one-out で条件を選び直し、外した正例が拾えるかを確かめた
(出力 `out/l1_round/stability.csv`)。

| 通過率 | leave-one-event-out | leave-one-drive-out |
|---|---|---|
| 1% | 4/9 | 4/9 |
| 2% | 4/9 | 5/9 |
| 3% | **6/9** | **5/9** |
| 5% | **8/9** | **8/9** |

**3% での 9/9 はそのまま外部データでは再現しない。** 汎化はおよそ 5〜6/9。
一方、選ばれる条件自体は全通過率で一貫しており、
**ax減速 2.0〜3.0 と ay 2.0〜3.0 の組み合わせ**に集中する。
**枝の構成は安定、閾値の細かい値は不安定**というのが正確な読み方。

## 5. commaCarSegments での実測 — Toyota 4 車種 / 587.1 時間

comma2k19 で固定した閾値を**車種ごとに調整せず**当てた
(`scripts/l1_apply_ccs.py`、出力 `out/l1_ccs_v2/`)。35,226 セグメント。

| 指標 | 標準 | 高圧縮 | 1 段階厳 |
|---|---|---|---|
| 2 秒窓 通過率 | 7.25% | 5.76% | **3.21%** |
| 候補を含む 60 秒 segment 率 | 51.4% | 45.2% | **32.8%** |
| 削減できる segment 率 | 48.6% | 54.8% | **67.2%** |
| `multi_evidence` 保持 | 100% | 100% | **100%** |
| `high_evidence` 保持 | 99% | 99% | **99%** |
| `activation_only` 保持 | 100% | 100% | **100%** |
| `physics_only` 保持 | 73% | 73% | 70% |

**車種差は小さい。** 高圧縮で 5.46〜5.90%、1 段階厳で 3.02〜3.40% (幅 0.38 ポイント)。
閾値を車種ごとに調整する必要はない。

**ただし comma2k19 の 2〜3 倍になる。** comma2k19 では標準相当が 4.19%、
高圧縮相当が 3.00% だった。走行内容の違い (commaCarSegments は多様な地域・
車両 1,000 台超、comma2k19 は 1 台のカリフォルニア高速道路中心) と考えられる。

### フラグの寄与

制御フラグを足したことによる通過率の増分は **+0.008〜0.010 ポイント**でほぼゼロ。
フラグが立つ窓は全体の 0.02〜0.05% しかない。**無条件通過にしてもコストは
発生しないので、取りこぼしを防ぐ保険として入れる価値がある。**

運動量だけで見ると閾値を締めた影響がはっきり出る。

| 等級 | 標準 (運動量のみ) | 高圧縮 (運動量のみ) | 1 段階厳 (運動量のみ) |
|---|---|---|---|
| `multi_evidence` | 100% | 100% | 100% |
| `high_evidence` | 86% | 81% | **64%** |
| `activation_only` | 69% | 51% | **26%** |

`activation_only` は運動量だけなら 26% まで落ちるが、**フラグで全件拾い直されて
100% になる。**

### 窓と segment の乖離

窓で 3.21% に絞っても 60 秒 segment では 32.8% が残る。候補窓が segment 内に
散在するためで、通過 segment あたりの平均通過窓数は 3.8〜4.2 窓 (中央 3 窓 = 6 秒)。

* **segment ファイル単位で間引く**なら削減率の上限は 67%
* **窓単位で後段を絞る**なら 96.8% を削減できる

## 6. 速度だけで決める除外

**低速除外 (`v >= 5 m/s`)。** 通過側にも掛ける。停車中の横 G やヨーは雑音で、
拾っても意味がない。comma2k19 で通過率 3.20% → 3.00% (6.3% 削減)、risky 損失 0。

**定常除外 (10 秒の車速レンジ < 1 m/s)。** これは**通過率を下げる処理ではない**。
「イベントトリガが立つ窓は必ず残す」ので、通過窓は定義上すべて残る。
下がるのは「そもそも評価しなくてよい時間」の量なので、別指標として扱う。

| 指標 | 値 (4 車種 587 時間) |
|---|---|
| 定常区間 | **全走行時間の 35.8%** |
| 速度ゲート通過 (`v >= 5`) | 85.7% |
| L1 通過窓のうち定常区間内 | 標準 4.9% / 高圧縮 6.1% |

**定常区間 35.8% は後段の decode とイベント判定を省略できる。** 通過窓のうち
定常区間にあるのは 5〜6% だけなので、安全条件を守っても省略できる時間は
ほとんど削られない。車種別は Prius 39.0% / Corolla 36.4% / RAV4 34.7% /
Highlander 33.4%。

## 7. Spark での形

**shuffle は `GROUP BY drive_id, segment, win_id` の 1 回だけ。** 判定は純粋な
列 filter で、rolling・lag/lead・UDF・as-of join を使わない。

```sql
-- 1. 窓 ID 付与 (列式のみ、shuffle なし)
WITH decoded AS (
  SELECT drive_id, segment, sig, t, value,
         CAST(FLOOR(t / 2.0) AS INT) AS win_id
  FROM raw_can
  WHERE address IN (0x0B4, 0x024, 0x226, 0x3B7)   -- L1 に要る 5.7% だけ
),
-- 2. 窓ごとの集約 (これが唯一の shuffle)
win AS (
  SELECT drive_id, segment, win_id,
         MAX(CASE WHEN sig='speed'   THEN value END) AS v_max,
         MIN(CASE WHEN sig='accel_x' THEN value END) AS ax_min,
         MAX(CASE WHEN sig='accel_y' THEN value END) AS ay_max,
         MIN(CASE WHEN sig='accel_y' THEN value END) AS ay_min,
         MAX(CASE WHEN sig='abs'     THEN value END) AS abs_f,
         MAX(CASE WHEN sig='vsc'     THEN value END) AS vsc_f,
         MAX(CASE WHEN sig='pcs'     THEN value END) AS pcs_f,
         MAX(CASE WHEN sig='slip'    THEN value END) AS slip_v
  FROM decoded GROUP BY drive_id, segment, win_id
)
-- 3. L1 判定 (純粋な filter。shuffle なし)
SELECT * FROM win
WHERE (v_max >= 5.0 AND (ax_min <= -2.5 OR GREATEST(ABS(ay_max), ABS(ay_min)) >= 2.0))
   OR abs_f > 0.5 OR vsc_f > 0.5 OR pcs_f > 0.5
   OR (slip_v > 3.5 AND slip_v <= 4.5)
```

キーに `drive_id, segment` を含むので、入力をドライブ単位でパーティションして
おけばパーティション内で閉じ、実質 shuffle は発生しない (map-side aggregation で
完結)。segment 単位の絞り込み
(`SELECT drive_id, segment, MAX(pass) GROUP BY drive_id, segment`) も同様。

**10 秒定常判定だけが例外**で、前後 2 窓を見るため `Window.rangeBetween` が要る。
これは窓サマリ (生データの 0.1% 以下) に対する操作なので、L1 本体には含めず
後段の省略判定として分離する。定常判定を外しても L1 の通過率・保持率は変わらない。

|---|---|---|
| 生 CAN 全メッセージ | 約 87 億行 | 100% |
| L1 に要るアドレスのみ | 約 5 億行 | 5.7% |

## 8. わかっていないこと

* **正例が 9 件しかない。** 閾値の細かい値は leave-one-out で不安定
  (3% で held-out 5〜6/9)。判断の確度を上げるにはラベル数を増やすしかない。
* **保持率の評価対象が 2 系統ある。** commaCarSegments 側は `direct_slip` の
  事象 (滑り系、フラグで守られる)、comma2k19 側は人手 risky (ヒヤリハット一般、
  フラグが無い)。**フラグを伴わないヒヤリハットは閾値を締めるほど落ちる**ので、
  高圧縮と 1 段階厳の選択は「滑り系を確実に取る」か「ヒヤリハット一般も広く取る」
  かの判断になる。
* **comma2k19 と commaCarSegments で通過率が 2〜3 倍違う。** 走行内容の違いと
  みているが、確かめていない。
* **`physics_only` は 70〜73% しか残らない。** 制御作動がなく物理挙動だけの事象は
  フラグの保護が効かない。L1 の設計上の割り切り。
* **速度ゲートを入れるかどうかを決めていない。** 外すと通過率は +0.7〜3.3pt
  増えるが `physics_only` が 6〜7pt 上がる (§3 の ablation)。5 m/s 未満で起きる
  滑りをどれだけ取りに行くかの判断で、まだ根拠が足りない。
* **フラグ枝を comma2k19 で検証できない。** 対象車両 (RAV4 2016) に
  ABS / VSC / PCS / `slip_warn` のチャネルが無い。フラグの効きは
  commaCarSegments の `direct_slip` 事象でしか測れておらず、
  人手 risky に対して同じだけ効くかは未確認。
